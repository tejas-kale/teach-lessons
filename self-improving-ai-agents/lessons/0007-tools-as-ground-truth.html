Lesson 7 of 14 · Self-Improving AI Agents

Tools as ground truth

Three places feedback can come from — the environment, an execution, or the model's own principles — and why the quality of your error messages is an agent-performance parameter.

≈10 minutes · Lecture 4 · Where verification stops being a model and becomes the world

Lessons 4 to 6 built increasingly sophisticated machinery for judging outputs with models. Lecture 4 makes the obvious point that has to be made somewhere: the best verifier is not a model at all. It is something that happened. Code ran or it didn't. The query returned 400 rows or 0. The API accepted the payload or rejected it with a reason.

The lecture organises this around three papers, distinguished by where the feedback originates.

ReAct: interleaving thought and action

The idea¹ is now so absorbed into how models behave that its novelty is easy to miss. Before it, you had two separate lineages: chain-of-thought models that reasoned beautifully but were ungrounded and hallucinated confidently, and tool-using models that acted but did not visibly reason. ReAct interleaves them — thought → action → observation, repeatedly — with the thought appended to the context so the next action is conditioned on it.

The gain is precisely on the tasks where reasoning alone fails for lack of facts: multi-hop question answering, fact verification, web navigation. Reasoning alone hallucinates; acting alone flails. Together, the observations correct the reasoning and the reasoning directs the actions. A useful detail: ReAct alone does not always beat chain-of-thought, but ReAct combined with self-consistency does. Grounding and sampling are complementary, not substitutes.

Modern frontier models do this inside their chain of thought without being asked, and models like Qwen exhibit it because they were distilled on traces of this shape. That is why the paper reads as obvious now. What is not obsolete is its structural claim: an interleaved trace of thought, action and observation is far more interpretable and debuggable than either half alone — which is why you should log all three.

The named failure mode is error cascading. One wrong observation early poisons every subsequent step, and the model rarely revisits it. Lesson 13 returns to this, since it is the dominant failure of long-horizon runs.

RLEF: the public/private test split

RLEF² trains coding agents with reinforcement learning where the actions are code and the observations are execution feedback. The loop: generate a solution, run it against public tests, feed failures back for another attempt, and — once it passes — compute the training reward from a held-out private test set.

That separation is the transferable idea, and it is not about RL. Whenever your agent iterates against a check, hold some checks back. If it retries until the assertions pass, the assertions have become the specification, and you have no evidence about anything they don't cover. This is Goodhart's law with a tighter loop, and the fix costs nothing: split your checks, show half, score on the other half.

Your error messages are a hyperparameter

RLEF's measured finding is about repair behaviour: with execution feedback in the loop, errors fall turn over turn and the model's edits become targeted repairs — it fixes the part that broke. Without the loop, later attempts are not reliably better; it rewrites rather than repairs. The feedback text itself ("execution timeout") is what makes the difference, separately from the binary pass/fail used as the training reward.

So: an agent handed "AssertionError" has almost nothing to work with, while the same agent handed the failing input, the expected value, the actual value and a stack trace can usually fix the bug on the next turn. If you wrap tools for agents, the richness of the failure path is doing more work than your prompt is.

One caveat on how far this goes. CodeContests problems are short — a few lines. Whether binary pass/fail is sufficient there and richer traces become necessary on larger problems was raised in the lecture as a student's conjecture, and the lecturer agreed it was plausible and untested. Treat it as a good hypothesis about your own codebase rather than a result.

Check yourself

Your agent retries a data-cleaning task until all your validation checks pass. What does a clean run now tell you?

The checks stopped being an independent measurement the moment they became a target the agent optimises against. It may have dropped the offending rows, coerced a type to silence a complaint, or special-cased the failing key. Hold back a validation set the agent never sees, and score there. B overstates it — iterating against checks is good and you should do it, you simply cannot also use those checks as your evidence.

Constitutional AI: feedback when there is no world to consult

Sometimes nothing can be executed. Constitutional AI³ handles that case by replacing human preference labels with a written constitution — a set of explicit principles — and having the model critique and revise its own output against them. Supervised stage: respond, critique against a principle, revise, then train on the revisions. RL stage: a preference model built from the constitution scores responses, and the policy optimises against it.

Two things to take from it. First, the mechanism is self-critique made specific: with a constitution of 16 written principles, the model is not asked "is this good?" but "does this violate this named principle?" — the same move as replacing a Likert scale with a binary checklist in Lesson 5, and it works for the same reason. Second, the results are honestly presented as a Pareto frontier between helpfulness and harmlessness rather than a free win. You are trading, and the constitution is where you write down the trade.

A caution the lecture adds, pointing at the follow-on literature: getting a model to critique itself is often harder than it looks, because it is overconfident about what it doesn't know — and a consensus of other models frequently critiques it better. That is Lesson 5's independence argument arriving from a different direction. Where you can afford it, prefer a critic from another model family over self-critique.

The generalisation for your work: a "constitution" is just an explicit, written statement of what a good output must satisfy in your domain — a house style for analyses, a set of statistical practices, the caveats a report must always carry. Written down, it becomes both a critique prompt and an eval rubric. Most teams keep this knowledge in reviewers' heads, where an agent cannot reach it.

Design rules for agent-facing tools

Synthesising the lecture into what to actually change:

  • Return rich failures. Expected vs actual, the offending input, the stack trace. Prefer a 400-word error to a boolean.
  • Make tools verifiable, not just callable. A tool that reports what it did — rows written, files changed, bytes read — gives the agent an observation to reason about. One that returns "OK" gives it nothing.
  • Fail loudly rather than degrading silently. A tool that returns an empty result on error teaches the agent that its approach worked.
  • Split checks into shown and held-out. Non-negotiable once anything iterates.
  • Write the constitution down for domains with no oracle, and use the same document as critique prompt and eval rubric.
  • Log thought, action, and observation separately. When a run goes wrong you need to know whether the reasoning was bad or the observation was — they demand completely different fixes.
Retrieval practice

Take a tool your agents call regularly. What does it return on failure? Rewrite that failure message as you would want an agent to receive it, then say what the agent could now do that it previously couldn't.

Typical before: Error: query failed. After: the failing SQL, the database's error text, the line and column, the schema of the tables referenced, and — where cheap — a hint such as "column user_id not found; the table has userId". The agent goes from guessing at a rewrite (and often rewriting the whole query, losing correct parts) to making a one-token fix. The general principle: return whatever a competent colleague would need to fix it without asking you a follow-up question. That framing decides nearly every case.

What you can now do

You can classify a feedback source as environmental, execution-based, or self-critique, and you know their relative strength. You have the public/private split as a defence against your own agent gaming your checks, and a concrete rule for what tools should return. Rich failures are the cheapest performance improvement in this entire course.
