Lesson 8 of 14 · Self-Improving AI Agents

Planning and multi-step reasoning

Search over actions instead of over answers — and the observation that most of a model's reasoning didn't need to be sequential in the first place.

≈10 minutes · Lecture 5 · Where sampling becomes search

Everything so far treated a task as one shot: generate candidates, pick one. Real agent work is a trajectory — a sequence of actions where each changes what is possible next. Sampling k complete trajectories is enormously wasteful, because they share prefixes, and it gives you no way to abandon a bad path early.

The move is to search the tree of actions rather than the set of answers.

LATS: Monte Carlo tree search, with a language model

Language Agent Tree Search¹ imports MCTS wholesale into agent land. Six stages, cycling: selection, expansion, evaluation, simulation, backpropagation, reflection.

The distinction from earlier verifier-guided search matters: a PRM (Lesson 4) scores reasoning steps, whereas LATS scores the outcomes of actions taken in the world. Selection uses UCT — value plus a bonus for nodes visited rarely relative to their parent — which is the standard machinery for balancing exploitation against exploration.

Results were strong on multi-hop QA and on web shopping, without fine-tuning. But two limitations are decisive for practitioners, and the lecture names both:

  • Cost. Expansion, simulation and backpropagation multiply calls, and the paper does not analyse the cost–benefit frontier at all.
  • Irreversibility. Tree search assumes you can back up. If an action sends an email, charges a card, or drops a table, there is no backing up. Search is only available where the environment is resettable or read-only.

That second constraint is the one that decides where you can use this. Read-only analysis over a warehouse: searchable, and cheaply — branch freely, nothing is harmed. A pipeline that writes to production: not searchable, unless you can run it against a sandbox or a transaction you can roll back. Building that sandbox is often the enabling investment, not the search algorithm.

Check yourself

Which agent workflow is the best candidate for tree search over actions?

Read-only exploration with many plausible paths and a cheap undo — abandoning a query costs a few seconds. The other three all take irreversible actions in the world; searching them means actually sending, migrating or posting down every branch you explore. The general test: can I abandon a branch at no cost? If not, you need a sandbox before you need a search algorithm.

Spring: most of that reasoning wasn't sequential

Reasoning models think longer on harder problems, and longer thinking correlates with higher accuracy — visible in DeepSeek-R1's training curves, where response length rises alongside benchmark scores. That is the good news. The bad news is latency and cost: you wait, and you pay, for every sequential token.

Spring² starts from a sharp observation: inspect a long reasoning trace as a dependency graph and large parts of it are independent. The model tries alternatives, decomposes into sub-tasks, checks separate conditions — and generates all of it in a strict line because that is the only thing autoregression permits.

The method is a nice example of manufacturing training data with models. Take reasoning traces from a strong model; use a second model to segment each trace into steps, tag each step as planning or execution, and annotate the dependencies between steps. That gives you a DAG, which you can repack so independent steps sit in parallel groups. Fine-tune on the repacked traces and the model learns to emit plans and their parallel executions explicitly, which the harness can then dispatch concurrently.

The result that wasn't the goal

The project set out to cut sequential tokens — a roughly 40% reduction on maths. It also raised accuracy (about 3.5 points over the base distilled model), and the gains transferred out of domain to tasks it was never trained on. Being made to state a plan before executing it appears to help the model think, independently of any parallelism won. Structure is not just a scheduling convenience.

A second observation, and this one you can apply without any fine-tuning: parallelism is high early and low late. Early on the model explores many independent directions; toward the end it converges on one line and drives it home. That is exactly the exploration-then-exploitation shape you should be designing your own workflows to have.

Translating into workflow design

You are not going to run MCTS or fine-tune a parallel planner. What you should take:

  • Make the plan an artefact. Have the agent emit an explicit plan before acting. It improves quality on its own, it lets you intervene at the cheapest possible moment, and it makes failures classifiable as bad-plan versus bad-execution.
  • Fan out the independent parts. Once there is a plan, its independent branches can run as separate agent calls — cheaper in latency, and each gets a clean context window (Lesson 13).
  • Explore early, converge late. Sample several approaches at the start when a branch costs little; commit to one before the expensive execution.
  • Keep the reflection. After a failed trajectory, have the agent write down why, and carry that note into the retry. It is the cheapest component of LATS and reportedly a large share of its benefit.
  • Build the sandbox. Every technique in this lesson requires cheap undo. A dry-run mode or a scratch schema is the prerequisite that unlocks all of them.
Retrieval practice

Take a multi-step workflow you run. Draw its dependency graph: which steps genuinely require the previous one's output, and which only appear sequential because you wrote them in a line?

Typical finding for an analysis pipeline: pulling three data sources, computing four metrics, and checking two data-quality conditions are all independent — only the synthesis at the end depends on everything. Written as one prompt, the agent does them in a line, accumulating everything in one context. Written as a plan plus fan-out, they run concurrently in fresh contexts and the synthesis step sees only clean summaries. That is a latency win and a context-hygiene win from the same change, which is why it is usually the highest-value restructuring available.

What you can now do

You can recognise when a task is searchable (cheap undo, many paths, checkable outcomes) and when it is not. You know why explicit planning helps even when nothing runs in parallel, and you have the exploration-early / convergence-late shape to design toward.
