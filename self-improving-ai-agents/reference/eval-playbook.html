Eval playbook

How to build an evaluation for one real agent workflow, which metrics mean what, and the failure taxonomy to classify runs against.

Two printable pages · Companion to Lessons 12 and 13

Build it in five steps

  • Choose one workflow and one decision. Not "evaluate our agents" — "should we switch the monthly-report agent to the fusion architecture?" An eval that cannot change a decision will not be maintained.
  • Collect 20–50 real tasks. From actual traffic, deliberately over-weighting the cases that went wrong. Synthetic tasks measure a distribution nobody uses.
  • Define success as a judgement you would defend. Binary where possible: would you have sent this? did the number match the source? Decompose anything subjective into yes/no criteria before scoring it.
  • Grade a baseline by hand. Painful, one-time, and it is what calibrates every automated judge you build afterwards. Thirty items is enough.
  • Split held-out from iteration set. Everything you look at repeatedly, you overfit — you as much as the agent.

Which metric answers which question

MetricDefinitionAnswersMisleads when
pass@1Succeeds on one attemptWhat a user sees todayYou quietly retry in production
pass@k / coverageSucceeds at least once in kIs the capability there at all?Reported as if it were product performance
pass^kSucceeds on all k attemptsCan this run unattended?Rarely — this is the honest one, and it will look bad
Cost per solved taskTotal spend ÷ successesIs the extra compute worth it?You ignore the cost of a wrong answer reaching someone
Steps to completionTool calls or turns usedIs it thrashing?Used as a target — shorter is not better if it fails
Recovery rateRuns that hit an error and still finished correctlyHow brittle is it?Errors are silently swallowed by tools

The pair to report together: pass@1 and pass^k. The first is optimistic, the second pessimistic, and the distance between them is your reliability problem stated as a number. A workflow at 85% pass@1 and 40% pass^5 is not an 85% workflow.

Failure taxonomy — classify every bad run

Do not record "failed". Record which of these, because each has a different fix.

ClassLooks likeFix in
Bad planSensible steps, wrong decomposition; solves an adjacent problemLesson 8
Missing capabilityNo sampled attempt gets close; coverage ≈ pass@1 ≈ 0Lesson 2, 9
Bad selectionA good attempt existed and was discardedLessons 4–6
Tool failureWrong observation, silent empty result, unhelpful errorLesson 7
Error cascadeOne early mistake propagates; the agent never revisits itLesson 13
Context rotDegrades late in long runs; forgets earlier constraintsLesson 13
Spec gamingPasses every check, satisfies nobodyLesson 7 — held-out checks
Right for wrong reasonsCorrect output, incoherent path; recurs unpredictablyLesson 4 — process checks

Twenty classified failures tell you more than two hundred unclassified ones. The distribution is your roadmap.

Traps

  • The judge is your selector. If the same component picks outputs and grades them, your eval is measuring its own preferences. Keep them separate.
  • Benchmark contamination. Public benchmarks leak into training sets. Use them for orientation, never as evidence about your workload.
  • Averaging away the tail. A mean hides the hard slice where all the value and all the risk sit. Report per-difficulty-bin.
  • One run per task. Agents are stochastic; a single run is a sample of size one. Minimum five.
  • Unpinned versions. A model updated underneath you invalidates every comparison. Pin, and re-baseline deliberately.
  • Grading only the output. The trace tells you why; the output only tells you whether. Log thought, action and observation separately.
  • No cost column. Accuracy without cost cannot justify or refuse an architecture change.

The weekly loop

  • Sample ten real runs. Classify each against the taxonomy — fifteen minutes.
  • Pick the largest class. Apply the corresponding dial from Tuning dials.
  • Re-run the eval set. Report pass@1, pass^k and cost per solved task.
  • Touch the held-out set only when deciding to ship, and never more than monthly.
