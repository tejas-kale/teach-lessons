Tuning dials

Every lever this course gives you over an agent, what it costs, and the symptom that should make you reach for it. Ordered roughly by effort.

One printable page · Start at the top and stop when the numbers move

Diagnose first

Before turning anything, run the two-number test from Lesson 3. Take 20–30 real tasks with known outcomes, run each 10 times, and record pass@1 (first run succeeded) and coverage (any run succeeded). Everything below branches on the result.

  • Coverage ≫ pass@1. The answer is in there and you are discarding it. Go to Selection. Do not buy a bigger model.
  • Coverage ≈ pass@1, both low. Genuine capability or context problem. Go to Capability.
  • Coverage ≈ pass@1, both high, but production feels worse. Your eval doesn't resemble production. Go to Measurement.
  • Wildly variable across runs of the same task. Reliability problem — measure pass^k, then go to Reliability.

Reliability — same task, different outcomes

  • Measure pass^k, not pass@k. Ten runs, count how many succeeded every time. This is the number that predicts an unattended production experience.
  • Lower temperature only after checking coverage. It reduces variance and reduces coverage together; if your selector is good, you want the diversity.
  • Add a gate, not a retry. Retrying until checks pass teaches the agent to satisfy checks. Hold some back (Lesson 7).
  • Bound the horizon. Shorter runs with checkpoints beat one long run, because error cascading compounds (Lesson 13).
  • Freeze what varies. Pin model versions, seeds where available, and prompt templates before concluding a change helped.

Measurement — the dial that makes every other dial legible

  • Twenty real tasks beat two hundred synthetic ones. Draw from actual traffic, including the failures that annoyed you.
  • Grade against a decision, not a score. "Would I have sent this to a stakeholder?" beats a 1–10 rating that clusters at 7.
  • Keep a held-out set you never iterate against. Everything you look at, you overfit.
  • Report cost per solved task, not accuracy alone. Every dial above spends money; the frontier you care about is quality per dollar.
  • Re-run the two-number test after each change. If coverage and pass@1 both moved, you changed capability. If only pass@1 moved, you improved selection. If neither moved, you changed nothing regardless of how it feels.

The order to try things

  • Measure (two-number test). Nothing below this line is meaningful without it.
  • Raise the thinking budget. Minutes of work.
  • Fix the tools' failure messages. Hours of work, often the largest single gain.
  • Generate n and fuse. One hour, almost always positive.
  • Add deterministic checks on the output, with some held back.
  • Build a rubric judge with binary criteria, calibrated on 30–50 labels.
  • Route by difficulty so the expensive path runs only where it is needed.
  • Stack critic–rank–fuse layers on offline work.
  • Only now consider a bigger model everywhere, or a fine-tune.
